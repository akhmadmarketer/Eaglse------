# Обязательность полей по стадиям — план настройки v1

## Назначение документа

Документ переводит раздел «Обязательность полей по стадиям» из
`docs/bitrix_crm_fields_v1.md` в конкретные коды полей и стадий фактического
портала и фиксирует способ настройки. Секреты, значения CRM-полей, сделки,
контакты и переписки в документ не попадают.

Дата снимка: 5 сентября 2026 года.

## Вывод read-only разведки: REST не подходит

Проверено на фактическом портале без единой записи:

- вебхуку доступно 465 методов; методов управления атрибутами полей
  (`crm.deal.fieldattribute.*`, `crm.item.fieldattribute.*`) среди них нет —
  оба варианта отвечают HTTP 404;
- `crm.item.details.configuration.getRequiredFields` не существует (HTTP 404);
- `crm.deal.userfield.list` для `UF_CRM_EAGLES_CLOSE_REASON` возвращает
  `MANDATORY='N'`, а `SETTINGS` содержит только `DISPLAY`, `LIST_HEIGHT`,
  `CAPTION_NO_VALUE`, `SHOW_NO_VALUE` — перечня стадий там нет;
- элемент того же поля в общей конфигурации карточки выглядит как
  `{'name': 'UF_CRM_EAGLES_CLOSE_REASON', 'optionFlags': '0'}`, хотя
  обязательность на стадии `LOSE` включена и работает.

Значит, обязательность по стадиям хранится вне доступной REST-модели и не
читается и не пишется через API. По правилу проекта это законный случай ручной
настройки: возможность недоступна через REST.

Следствие для проверки: подтвердить настройку можно только визуально в
интерфейсе. REST остаётся полезен для контроля побочных эффектов — после каждого
блока проверяем, что глобальная обязательность не изменилась (`MANDATORY=N`) и
что состав карточки остался прежним (41 поле, 6 проектных разделов).

## Фактические стадии основной воронки

Подтверждено методом `crm.dealcategory.stage.list` для воронки `0`:

`NEW`, `UC_JMBAX5`, `UC_XI4M3M`, `UC_2YCHH0`, `UC_4OCEJT`, `UC_KJBWTE`,
`UC_N9VQVU`, `UC_SXEQHN`, `WON`, `LOSE` — порядок и названия совпадают с
`docs/bitrix_implementation_status_v1.md`.

Все 41 проектное поле подтверждены на портале, у всех `MANDATORY=N`.

### `LOSE` — Закрытая неуспешная сделка

Настроено ранее: «Причина закрытия» (`UF_CRM_EAGLES_CLOSE_REASON`) обязательна
только на `LOSE`. Изменений не требуется.

### `NEW` — Новое обращение

Документ требует источник, ID чата и связь с клиентом. Все три значения
заполняет интеграция, а не человек. Обязательность в карточке заблокирует ручное
создание сделки менеджером и ничего не даст боту, потому что проверка стадии
происходит при сохранении карточки, а не при записи через REST.

Решение: на `NEW` обязательных полей не назначать; требование остаётся правилом
кода интеграции.

## Условная обязательность, которую Bitrix24 не выражает

Флаг привязывается к стадии, а не к значению другого поля. Поэтому в интерфейсе
не выражаются два требования документа:

- «дата контакта, только если согласована» — зависит от значения поля
  «Согласованный повторный контакт»;
- «комментарий для значения „другое"» на `LOSE` — зависит от значения поля
  «Причина закрытия».

Оба остаются необязательными в CRM, а проверка переносится в бизнес-правила
модели и в валидацию перед записью полей из `app.py`.

## Решения владельца от 5 сентября 2026 года

1. **`WON` не настраивается.** Ассистент не принимает оплату и не контролирует
   её — по крайней мере на текущем этапе. Поэтому поле-подтверждение оформления
   или оплаты не создаётся, и обязательных полей на `WON` не назначается.
   Требование документа «подтверждение оформления, оплаты или предоплаты»
   остаётся зоной ответственности менеджера вне CRM-обязательности.
2. **Стадии менеджера не трогаем.** `UC_4OCEJT`, `UC_KJBWTE`, `UC_N9VQVU`,
   `UC_SXEQHN` остаются без обязательных полей. Раздел «Обязательные данные»
   стадии `UC_N9VQVU` в `docs/bitrix_sales_funnel_v1.md` не переносится в CRM:
   полей под «что предложено», «когда отправлено» и «какие вопросы остались»
   нет, а создавать их до реальной практики продаж преждевременно.

Итоговая область настройки: три стадии бота — `UC_JMBAX5`, `UC_XI4M3M`,
`UC_2YCHH0`. Стадия `LOSE` настроена ранее.

## Фактическая сила обязательности: проверено по значениям списков

Read-only аудит значений показал, что у всех восьми списочных полей чек-листа
задано значение по умолчанию: `unknown`, `unknown_intent`, `not_discussed`,
`none`, `not_started`. Bitrix24 подставляет его сам, поэтому проверка
обязательности на таких полях проходит автоматически и сохранение карточки не
блокирует.

Реально блокируют сохранение только три текстовых поля, пустые по умолчанию:

- `UF_CRM_EAGLES_STATE_REASON` — «Основание состояния» на `UC_XI4M3M`;
- `UF_CRM_EAGLES_MANAGER_SUMMARY` — «Резюме для менеджера» на `UC_2YCHH0`;
- `UF_CRM_EAGLES_MISSING_DATA` — «Недостающие сведения» на `UC_2YCHH0`.

Это не повод убирать значения по умолчанию: проект сознательно сделал
неизвестность явным состоянием, чтобы ни модель, ни менеджер не выдумывали
факты. Списочные поля отмечаются для полноты правила — проверка сработает на
сделках, где значение всё же оказалось пустым.

Вывод для приоритетов: обязательность по стадиям дисциплинирует менеджера, но не
является технической защитой. Для бота эквивалентные правила должны быть
реализованы проверками в `app.py` перед записью полей и сменой стадии.

## Чек-лист настройки: по полям, а не по стадиям

Настройка выполняется в карточке поля, где отмечаются сразу все его стадии.
Два поля требуются на двух стадиях каждое, поэтому настраивать нужно по полям —
иначе второй проход снимет отметку, поставленную на первом.

Итого 11 полей. Для каждого: карточка сделки → настройки поля → «Обязательно на
стадии» → отметить ровно перечисленные стадии → сохранить.

## Состояние: настройка завершена

Все 11 полей чек-листа настроены владельцем вручную 5 сентября 2026 года.
Вместе с «Причиной закрытия», настроенной ранее, обязательность по стадиям имеют
12 полей.

Проверка `bitrix_stage_mandatory_check.py` подтверждает: 10 стадий, 41 поле с
`MANDATORY=N`, шесть проектных разделов карточки, дублей нет, критичных проблем
нет.

Подтверждённое поведение Bitrix24: при включении обязательности поле переезжает
в главный раздел карточки «О сделке». Так переехали девять полей. Владелец решил
раскладку не восстанавливать, поэтому `bitrix_crm_card_layout_setup.py --apply`
больше запускать нельзя — он вернёт поля обратно и будет воевать с Bitrix24.

## Порядок настройки

Три блока, после каждого — проверка:

1. поля 1–5 чек-листа (закрывают стадию «ИИ: консультация и прогрев»);
2. поля 6–7 (закрывают «Отложенный интерес»);
3. поля 8–11 (закрывают «Требуется менеджер»).

Проверка после каждого блока:

- в интерфейсе: открыть настройку каждого поля блока и убедиться, что отмечены
  только стадии из чек-листа;
- через REST read-only: `python3 bitrix_stage_mandatory_check.py` — скрипт
  подтверждает, что глобальная обязательность полей осталась `N`, что в общей
  конфигурации карточки по-прежнему 41 проектное поле в шести разделах и что
  дублей не появилось.

Скрипт не может прочитать сам перечень стадий — этого не умеет REST. Он
проверяет отсутствие побочных эффектов; сам факт отметки стадий подтверждается
глазами в интерфейсе.

Пустые сделки для проверки не сохраняются.

При проверке выяснилось, что три раздела, созданных владельцем вручную, имеют
сгенерированные Bitrix24 коды: «Основное о запросе» — `user_fwhr2ocm`, «Клиент и
задача» — `user_0vpb9awf`, «Состояние, барьер и квалификация» — `user_jc31hcaf`.
Три раздела, созданных через REST, сохранили проектные коды.

На работу это не влияет: и `bitrix_crm_card_layout_setup.py`, и
`bitrix_stage_mandatory_check.py` сопоставляют разделы по названию, а не по коду.
Переименовывать разделы в интерфейсе без обновления обоих скриптов нельзя.
