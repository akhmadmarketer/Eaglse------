# Eagles Instagram bot

Локальный прототип связывает Instagram Direct с OpenAI через Открытую линию
Bitrix24:

```text
Instagram → Bitrix24 → локальный обработчик → OpenAI → Bitrix24 → Instagram
```

## Подготовка

Установите зависимости:

```bash
python3 -m pip install -r requirements.txt
```

Создайте `.env.local` по примеру `.env.example` и заполните значения. Файл с
секретами исключён из Git.

## Прокси в окружении разработчика

Если в окружении заданы переменные прокси, перед запуском нужно два действия:

```bash
unset ALL_PROXY all_proxy
export no_proxy=127.0.0.1,localhost NO_PROXY=127.0.0.1,localhost
```

Первое обязательно: `httpx` не понимает схему `socks://`, и клиент OpenAI падает
при создании с `ValueError: Unknown scheme for proxy URL`. `HTTPS_PROXY` при этом
сохраняется — через него обработчик и ходит в OpenAI.

Второе не даёт отправлять запросы к собственному серверу в прокси.

## Запуск

Запустите обработчик:

```bash
python3 app.py
```

Проверка сервера:

```bash
curl --noproxy '*' http://127.0.0.1:8000/health
```

## Публичный HTTPS-туннель

Bitrix24 должен достучаться до обработчика снаружи. Запускать туннель следует
через обёртку:

```bash
./run_tunnel.sh
```

Скрипт поднимает туннель, печатает адрес вида
`https://<случайный>-<ваш IP>.free.pinggy.net`, сразу привязывает его к боту и
держит окно открытым. Журнал — `logs/tunnel.log`.

Провайдер — `pinggy.io` по SSH: ни установки, ни регистрации не требует.
Проверенные 5 сентября 2026 года альтернативы не подошли:

| Провайдер | Что происходит |
|---|---|
| `localhost.run` | `Permission denied (publickey)` и для `nokey@`, и с ключом |
| ngrok | `ERR_NGROK_9040`: агентам с IP этой машины подключаться запрещено |
| serveo.net | соединение не устанавливается |

Особенность бесплатного туннеля pinggy: он живёт 60 минут. Обёртка сама
переподключается на 55-й минуте, получает новый адрес и заново привязывает его к
боту, поэтому вмешиваться не нужно — в журнале появится строка «туннелю почти
час».

Прямой доступ к `a.pinggy.io:443` из этой сети пропадает: TCP-соединение
зависает, не доходя до приветствия SSH, и ssh молчит до таймаута. Поэтому
обёртка сначала пробует прямой маршрут, а через 15 секунд повторяет попытку
через socks-прокси, который уже используется для OpenAI:

```text
маршрут direct не дал адреса
прямой маршрут не сработал, идём через socks 127.0.0.1:10808
туннель поднят: https://igrag-217-60-251-15.free.pinggy.net (маршрут socks)
```

Сработавший маршрут запоминается и используется первым при следующем
переподключении. Адрес прокси берётся из `EAGLES_SOCKS_PROXY`, иначе из
`ALL_PROXY`, иначе `127.0.0.1:10808`. На публичный адрес маршрут не влияет:
туннель отдаёт сам pinggy.

Отдельно о сторожевой проверке. Туннель может перестать работать на стороне
провайдера, при этом ssh-клиент остаётся жив, а TCP-соединение — в состоянии
`ESTAB`. Изнутри такой обрыв невидим: Bitrix24 стучится на мёртвый адрес, бот
молчит, в `logs/app.log` пусто. Поэтому обёртка каждые 30 секунд проверяет адрес
снаружи и после двух отказов подряд поднимает туннель заново.

Без обёртки то же самое вручную:

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u all_proxy \
  ssh -p 443 -R0:localhost:8000 a.pinggy.io
```

Тогда после каждого обрыва и каждый час адрес придётся привязывать самому.

## Регистрация бота в Bitrix24

Бот регистрируется один раз:

```bash
python3 register_bitrix_bot.py https://<адрес туннеля>/bitrix/events
```

Сохраните числовой `bot_id` из ответа в `B24_BOT_ID`.

Дальше адрес туннеля меняется при каждом запуске, и его нужно не регистрировать
заново, а обновлять — иначе в портале появится второй бот-дубль:

```bash
python3 register_bitrix_bot.py --update https://<новый адрес>/bitrix/events
```

Скрипт не выводит URL вебхука и токен бота.

Получите список Открытых линий и подключите бота к нужной линии:

```bash
python3 bitrix_openline.py list
python3 bitrix_openline.py connect 1
```

## Работа со сделками

Каждое обращение из Instagram Bitrix24 сам превращает в лид и — из-за простого
режима CRM — сразу конвертирует его в сделку основной воронки на стадии «Новое
обращение». Обработчик сделки не создаёт: он находит готовую по чату Открытой
линии (`imopenlines.dialog.get` → `entity_data_2`), а на случай закрытого чата
дублирует связь в поле «ID чата Открытой линии».

Перед ответом обработчик читает стадию сделки, её проектные поля и контакт,
передаёт это модели блоками `CRM_CONTEXT` и `CONTACT_CONTEXT` и получает от неё
одно структурированное решение по `schemas/eagles_sales_decision.schema.json`.
Решение проходит проверку приложением, и только разрешённое попадает в CRM.

Бот отвечает и пишет в сделку только на стадиях «Новое обращение», «ИИ:
консультация и прогрев» и «Отложенный интерес». Если сделка ушла дальше или к
чату подключился сотрудник, бот молчит и ничего не меняет. Разрешены только
переходы `NEW → ИИ: консультация`, `ИИ: консультация ↔ Отложенный интерес` и
переход в «Требуется менеджер»; любой другой блокируется. При передаче менеджеру
ответ клиенту уходит только после успешной записи в сделку.

Сделка ищется по контакту, а не по связи чата: из чата берётся `CONTACT_ID`, а
затем открытая сделка контакта в основной воронке (`CLOSED=N`). Связь чата с CRM
в Bitrix24 одноразовая и через REST не переписывается, поэтому источником истины
она быть не может. Заодно это верно по смыслу: сделка — одна попытка продажи, а
чат — постоянные отношения, и вторая покупка клиента должна стать отдельной
сделкой, иначе воронка перестаёт считаться.

Если открытой сделки нет, обработчик заводит новую на стадии «Новое обращение» —
но только когда модель определила обращение как продажное (`request_type` равен
`new_sale` или `upsell`). Жалоба, вопрос действующего клиента по своей услуге,
деловое предложение и нецелевое обращение продажную сделку не создают. Пока
`request_type` равен `unknown`, бот отвечает и ждёт: сделка появится, когда
появится сигнал, и всё уже собранное запишется в неё сразу. Создание работает
только в режиме `apply`.

Перед передачей менеджеру бот собирает минимум: для кого услуга и возраст
ребёнка, уровень подготовки и удобное время. Недостающее он спрашивает не более
чем за два хода, а при просьбе о человеке, жалобе, вопросе о здоровье, оплате
или договоре передаёт сразу, без уточнений.

Неподтверждённые данные не являются поводом для передачи менеджеру. Если у факта
статус `needs_confirmation` или `incomplete`, бот называет известное значение,
оговаривает необходимость уточнения и продолжает консультацию. Передача
происходит, когда клиент хочет записаться, оформить или оплатить, просит
человека, сообщает о травме, жалуется либо запрашивает расчёт.

Режим работы задаётся переменной `EAGLES_CRM_MODE`:

| Значение | Поведение |
|---|---|
| `off` | сделка не читается и не пишется, бот только отвечает |
| `plan` | сделка читается, план записи попадает только в журнал (по умолчанию) |
| `apply` | план записи выполняется в Bitrix24 |

Строка `crm plan deal=... stage=...->... fields=...` в `logs/app.log` показывает,
что именно было бы записано. Начинать стоит с `plan`, а `apply` включать после
разбора нескольких таких строк.

## Вымышленные данные для отладки

В реальном снимке сайта (`knowledge/dynamic/`) нет ни одного факта со статусом
`confirmed`: цены помечены `needs_confirmation` и `incomplete`, расписание —
`conflict`, мероприятия — `past`. На таких данных бот честно отвечает «нужно
уточнить» почти на любой вопрос, и проверить качество консультации невозможно.

Для стенда есть каталог `knowledge/mock/` — вымышленные цены, расписание,
тренеры и условия со статусом `confirmed`. Имена тренеров придуманы специально,
чтобы тестовые сведения не приписывались реальным сотрудникам.

```bash
EAGLES_KNOWLEDGE_MOCK=1 EAGLES_CRM_MODE=apply python3 app.py
```

При включении в журнал попадает предупреждение, а в стартовой строке появляется
`knowledge=mock`. **Не оставляйте режим включённым на канале, где пишут
настоящие клиенты:** бот будет называть выдуманные цены как подтверждённые. Без
переменной загружается реальный снимок, каталог `mock` в промпт не попадает.

## Локальные проверки

### Длинный диалог в терминале

В одном окне терминала запустите сервер:

```bash
python3 app.py
```

Во втором окне запустите интерактивный тест:

```bash
python3 test_chat.py
```

Бот сохраняет последние 20 сообщений отдельно для каждого локального сеанса и
чата Bitrix24. Команда `/reset` начинает разговор заново, `/exit` завершает
тест. Память хранится только в оперативной памяти и очищается после перезапуска
сервера.

Автотесты:

```bash
cd tests && python3 -m unittest test_app test_decision
```

Прямой запрос к OpenAI:

```bash
curl -X POST http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"session_id":"test-1","message":"Здравствуйте! Какие направления у вас есть?"}'
```

Имитация события Bitrix24 без отправки ответа в портал:

```bash
curl -X POST http://127.0.0.1:8000/bitrix/events \
  -H 'Content-Type: application/json' \
  -H 'X-Local-Test: 1' \
  -d '{
    "event":"ONIMBOTV2MESSAGEADD",
    "data":{
      "bot":{"id":456},
      "message":{"id":1001,"chatId":112,"authorId":77,"text":"Здравствуйте!"},
      "chat":{"id":112,"entityType":"LINES"}
    }
  }'
```

`B24_APPLICATION_TOKEN` необязателен для короткого локального теста. Если он
заполнен, обработчик отклоняет события Bitrix24 с несовпадающим токеном.

## Журналы

Обработчик пишет в `logs/app.log` — файл с ротацией по 5 МБ и три архива, тот же
вывод дублируется в терминал. В журнале видно приход события от Bitrix24, причину
отклонения события, длительность запроса к OpenAI, отправку ответа и ошибки с
трассировкой.

Тексты клиентов по умолчанию не записываются, остаётся только длина сообщения и
технические идентификаторы. Для разбора конкретного диалога:

```bash
LOG_MESSAGE_TEXT=1 python3 app.py
```

После разбора переменную следует убрать. Уровень подробности меняется через
`LOG_LEVEL` (по умолчанию `INFO`). Каталог `logs/` исключён из Git.

## База знаний

Подготовленная база находится в каталоге `knowledge/`: постоянные сведения
в `static/`, изменяемые цены, тренеры, события и расписание в `dynamic/`.

В системный промпт модели попадают только эти два каталога. Служебные
`knowledge/README.md` и `knowledge/review-needed.md` — внутренние заметки о
неподтверждённых и противоречивых данных, и модель их не видит. Проверка
закреплена тестом в `tests/test_app.py`.

Чтобы заново получить технический снимок публичного сайта:

```bash
python3 scrape_academy_eagles.py --output /tmp/eagles-academy-snapshot.json
```

Вопросы из `knowledge/review-needed.md` остаются открытыми: пока они не закрыты,
цены, расписание и состав тренеров нельзя считать подтверждёнными.

## Настройка Bitrix24

Практическое состояние настройки CRM ведётся в
`docs/bitrix_implementation_status_v1.md` — этот файл читается первым.

Скрипты настройки:

```bash
python3 bitrix_crm_fields_setup.py          # план по пользовательским полям
python3 bitrix_crm_card_layout_setup.py     # план по разделам карточки сделки
python3 bitrix_stage_mandatory_check.py     # проверка обязательности по стадиям
```

Первые два без флага только читают и показывают план; запись выполняется с
`--apply`. Третий только читает.

## Текущие ограничения

- используется временный системный промпт, JSON Schema решения модели ещё не
  подключена;
- история диалога и защита от повторной обработки живут в оперативной памяти и
  теряются при перезапуске;
- контекст сделки из Bitrix24 не читается, поля CRM ботом не заполняются;
- запись, оплата и передача диалога сотруднику не реализованы.
